# 1.03 update walkthrough and feature verification

This is a local combined-release addition. No production migration, deployment,
iOS sync/build, installation, or App Store/TestFlight upload was performed.
The existing production API remains at `a7f2fcd` / schema 0122; the local working
preview is ready at schema 0124. These are deliberately different release states.

## Walkthrough behavior

`AppUpdateExperience` replaces Layout's standalone App Review mount and sequences
onboarding, the update walkthrough, and native App Review. The centered dialog
uses existing Radix focus trapping, keyboard dismissal, shared controls, charcoal
panels, CFFB blue, and the established sports typography. It greets the authenticated
manager, offers Next/Back, a ten-step progress indicator, Skip update, Close, and
Got it. Small viewports scroll the dialog rather than clipping its controls.

The topics are Weekly Challenges, refreshed UI/player headers, player graphs,
matchup record colors, name changes, player data/availability, real/mock draft
ordering, notification categories/Big Play retirement, and the App Store review
opportunity. Copy does not promise Apple will display StoreKit or manufacture
missing player results.

The opportunity is once per immutable account for release key `1.03`. It is
consumed at first presentation authorization, so dismissal, stopping mid-guide,
reinstall, another device, name changes, and later logins cannot start it again.
`POST /release-notes/1.03/claim` authenticates the actor, requires
`X-CFFB-Release-Account` as a stale-session precondition, and rejects owner fields.
The empty request body is strict; the result is `account_id`, `release_key`,
`authorization` (`granted` or `already_seen`), and `claimed_at`.

`user_release_notices` has a composite account/release primary key. The service
locks the existing account row before checking/inserting and commits before
returning a grant. A lost response can consume the opportunity; retries never
replay permission. In-flight claims are coalesced in the client for StrictMode
and transient route changes. Local storage is an optional account/version-scoped
suppression cache; the durable server receipt governs fresh devices. Late responses
cannot open another signed-in account's popup. The original account precondition
survives token refresh.

The popup waits for restored authentication, a usable safe screen, completed
onboarding, closed player/menu dialogs, document foreground, and completion of
native permission requests. It rechecks presentation safety after the server
responds. App Review stays blocked during that wait and throughout the popup.
The update receipt does not modify App Review's independent lifetime claim.
Failed requests show no false success and preserve server-side eligibility when
no receipt was committed.

The combined build retains the existing automatic native review flow: the next
confirmed iOS login or restored session for an unclaimed account requests Apple's
rating sheet as soon as the walkthrough closes and the screen/native scene are usable, without
an artificial three-second wait.
Apple's sheet provides the tappable 1–5 stars and App Store submission. There is
no custom star selector, rating-dependent routing, or recurring reminder. The
account's atomic lifetime review claim is preserved across versions, dismissal,
reinstall and other devices. Apple controls display and does not expose the
chosen rating to CFFB; TestFlight suppresses this sheet. Native invocation and
server claim verification are not proof of visible display or a submitted rating.

## Feature checks performed October 15

- **Name changes:** real browser changed the local test account from Weekly Preview
  to Weekly QA Verified through the confirmation dialog. The saved value and
  seven-day cooldown survived reload. Direct API overwrite returned 429 and kept
  the original last-change/next-eligible instants. PostgreSQL verified simultaneous
  account operations and exact expiry boundaries. A test assertion was corrected
  to compare instants rather than replace PostgreSQL's valid Eastern offset;
  production name-change logic was already correct.
- **Notification preferences:** toggled Trades off, reloaded and observed it still
  off, restored it, and confirmed persisted API state. No Big Play/long-play/
  touchdown controls appeared in Settings or their keys in API preferences.
- **Actual in-app delivery:** the local diagnostic API queued a test Projection
  event for an isolated league. The real notification worker processed it using
  fake external providers, history displayed it with an unread badge, and the
  browser's Mark All Read cleared the badge. No production sends or external
  push/email calls occurred.
- **Diagnostic fix discovered:** an account without league membership caused the
  diagnostic endpoint to raise an unhandled ValueError/HTTP 500. It now returns
  actionable 422. Multiple memberships formerly made an unbounded scalar query
  ambiguous; the diagnostic now chooses one stable owned membership. New regressions
  cover both cases and actual worker-to-history delivery. Production admin gating
  is preserved.
- **Big Play retirement:** regression coverage rejects new retired events and
  legacy key prefixes; cancels existing queued push/email/in-app attempts before
  rendering/fanout; hides old history before pagination/unread counts; prevents old
  taps; strips and clears legacy preferences globally and per league. Inert legacy
  columns remain for compatibility/history and cannot re-enable the feature.
- **Updated UI:** local desktop sidebar and navigation reached the full 720px
  viewport bottom; document width equaled the 1280px viewport. Phone-width popup
  screenshots were centered with no horizontal overflow. Position-colored player
  headers, graph rules, record highlights, draft ordering and Home challenge access
  passed their focused and full regression suites. An actual mock-board player
  card also rendered the WR purple gradient; the mock was exited without drafting
  or touching a league roster.
- **API environments:** local `/health/ready` reports 0124 ready. Production's
  read-only readiness reports 0122 ready; its runtime reports native App Review
  enabled. No deployment/configuration was changed during these checks.

## Physical-device boundary

After the owner connected and unlocked the iPhone, CoreDevice confirmed a connected
physical tunnel and read only the CFFB app record. The installed application is
**1.0.2, build 36**, `org.collegefantasyfootball.app`, an App Store installation
with no accessible developer container. It does not contain the later combined UI
and push fixes. Connecting a cable does not replace its bundled frontend.

No native package was built or installed during this verification. Physical APNs
banner/tap/background delivery of the updated implementation and actual StoreKit
presentation remain unverified until the matching combined app is installed.
Server acceptance, Swift policy assertions, mocks, browser tests and readiness
are not presented as proof of physical display. The signed prior build 38 also
predates the newly staged Weekly Challenges/walkthrough and is not the final
combined-release package.
